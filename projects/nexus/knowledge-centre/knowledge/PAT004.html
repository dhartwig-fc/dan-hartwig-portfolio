PAT004 · Network Intelligence

Circular Ownership

Does ownership eventually loop back to the originating entity?

Supporting questions:

Who ultimately controls the structure?

How many entities participate in the ownership cycle?

Is the circular ownership intentional?

Does the structure obscure beneficial ownership?

Does the structure create sanctions exposure?

Does the structure indicate elevated financial crime risk?

NI004 Circular Ownership identifies ownership structures where ownership relationships ultimately loop back to an originating entity.

The purpose of this intelligence product is to detect ownership cycles that may be used to:

  • Conceal beneficial ownership
  • Obscure control structures
  • Inflate balance sheet positions
  • Create artificial ownership independence
  • Hide related-party relationships
  • Reduce ownership transparency

Circular ownership structures are generally considered higher-risk because they can make control relationships difficult to identify.

Risk indicators

Risk

  • Circular ownership structure detected
  • Beneficial ownership obscured
  • Ownership transparency reduced
  • Cross-jurisdiction ownership cycle
  • Related-party control indicators

How this pattern looks

Engine sample · synthetic data

A worked example, step by step: one ownership cycle returned by fc-03's circular-ownership analytic over its own synthetic sample network of 20 entities and 20 ownership records, and the records the engine read around it. Every company is fictional. The engine's rule is the loop: it follows records of an ownership type from owner to owned and returns each distinct loop once, turned so that it starts at its first id in text order. This page's detection logic lists cross-border loops, control loops and beneficial ownership cycles, and its question asks whether circular ownership is intentional: the engine reads no country, counts a control record as ownership, reads no percentage, and does not decide intent. The engine then scores each finding with a network risk engine; four of the five figures behind that score describe the whole sample network and not the ring, and two are zero only because the analytic hands the engine nothing for them, so each step says only whether the engine's output holds a figure above zero. Three words are kept apart on this page: the engine's discovery label for the ring, the engine's level word for its score, and the band NEXUS publishes. The engine gives no alert line. The subject is the start of the ring NEXUS's adapter chose, the ring with the most members and the lowest start id where rings tie, not a choice the engine makes. This is the engine's own output for one sample ring, not a customer case.

Each step: what the engine states, and the rule behind it

  • found the engine's output holds it for the subject
  • not found the engine looked and its output holds none

  1. Circular ownership

    found

    What the engine statesThe engine's output holds an ownership cycle of 4 members that starts at Theta Investments Ltd (C007), numbered CYCLE_003 by the engine: Theta Investments Ltd (C007), then Iota Ventures Ltd (C008), then Kappa Global Ltd (C009), then Lambda Services Ltd (C010), then Theta Investments Ltd (C007)

    The ruleCircular ownership: the engine builds a graph from every record of an ownership type (owns, partial owner, shareholder, beneficial owner, ultimate owner, control) from the owner to the owned, follows it from each party, and reports a loop each time the walk returns to the party it started from, without passing any party twice. It turns each loop to start at its first id in text order, so one loop is one finding however it is entered, and it numbers the loops by position in its own sorted list: the number moves if a loop is added. It reads each record's type and its two ids and not its percentage, its confidence or any country. The step is found where the engine returned a ring with the subject as its start. The subject is always one of the engine's own findings, so this step is found for every finding the walk shows

    The ruleEntity risk: the engine reads a risk score from each entity record of the whole network it is given, a record with no such column reading as 0 (a blank value stops the engine), and takes the mean over all entities. The toolkit's entity file for this sample has no risk score column, so every entity reads 0 and this component is 0 whoever the entities are.   6. Relationship risk

    found

    What the engine statesThe engine's output gives relationship risk 37.82 of 100 for the network, at a weight of 20%, which is 7.564 points of the engine's score for this finding

    The ruleRelationship risk: the engine gives each relationship of the whole network a base figure by its type (ultimate controller 90, control 85, beneficial owner 80, trades with or transacts with 60, director of or shares contact with 55, shares address with 50, sanctions exposure 100, any other type 40; the engine's table spells the two shares kinds SHARES_CONTACT_WITH and SHARES_ADDRESS_WITH, so a record spelled SHARES_CONTACT or SHARES_ADDRESS reads as any other type), multiplies it by that relationship's own confidence and takes the mean over all of them, so many ordinary relationships dilute a severe one. The sample's 20 relationships are all OWNS, a type the engine's table does not list, so each reads as any other type (40), with confidences averaging 0.9455, so this component is 40 times 0.9455, which the engine rounds to two places, 37.82. It reads every relationship of the file and not the finding's own, so every finding of this sample run carries the same figure. A blank confidence value stops the engine, and a missing confidence counts as 1. Every relationship scores at least 40 times its own confidence, so this figure is above zero for any network with a relationship of some confidence: found here says the network has relationships, not that any is severe. The step is found where the engine's figure is above zero and not stated where it is zero

The analytic hands the engine no list of ownership paths, so this component is 0 in every run of this analytic, although the finding itself is an ownership chain: the chain is not handed over as a path to score.   8. Exposure risk

    found

    What the engine statesThe engine's output gives exposure risk 10 of 100 for the network, at a weight of 20%, which is 2 points of the engine's score for this finding

    The ruleExposure risk: the analytic hands the engine the finding itself as its one exposure indicator, and the engine reads its text: the finding's own fields (the typology tag, the cycle number, its start, its ids in order, its length and the discovery label), written out as Python prints a dictionary, field names included. The row the run keeps is that dictionary plus typology_id, typology_name and risk_assessment, which the analytic added afterwards, so the run holds the fields the text was read from. The engine's rule on that text: it adds 40 if the text contains SANCTION, otherwise 25 if it contains PEP, otherwise 20 if it contains ADVERSE or HIGH RISK, and otherwise 10 (capital letters are ignored, and a name that merely contains those letters counts: a name containing PEP would score 25), then 15 for each connected high-risk entity the network figures report, up to 45, capped at 100. The analytics engine's network figures hold a node count and an edge count and report no connected high-risk entity. The text of this finding contains none of those words, so the engine adds 10 for it. That 10 is what any finding of this kind gets when its text holds none of those words. The step is found where the engine's figure is above zero and not stated where it is zero. A figure here says the engine was handed something to read, not that anything about the subject is exposed

  9. Structural risk

    found

    What the engine statesThe engine's output gives structural risk 60 of 100 for the network, at a weight of 10%, which is 6 points of the engine's score for this finding

    The ruleStructural risk: the engine adds three points for each node up to 30, one and a half for each relationship up to 30, ten for each level of ownership depth up to 25, and 100 times the network's density up to 15, capped at 100. The analytics engine's network figures hold a node count and an edge count and no network size, ownership depth or density (it also returns lists of components, clusters, bridges, influence and exposure, which the risk engine does not read), so only the first two parts can score. This sample network has 20 nodes and 20 relationships, which the engine reads as 30 for the nodes and 30 for the relationships, 60 in all. It describes the whole network and not the subject, and every finding of this sample run carries it. The first part scores at least 3 for any network with a node, so this figure is above zero for any network with a node: found here says the network has size. The step is found where the engine's figure is above zero and not stated where it is zero. A figure here says the network is that large, not that it is risky

    The ruleRisk drivers: the engine builds a sorted list of named drivers from the whole network and the finding: Beneficial ownership relationship identified when ANY relationship of the network is of that type, Control relationship identified when any is a control relationship, Sanctions exposure relationship identified when any is of that type, Layered ownership structure when it is handed an ownership path of depth 3 or more (none is here), Large connected network when the network figures give a network size of 10 or more (the analytics engine gives a node count and no network size, so this driver cannot appear for these runs), Connected high-risk entities when the figures count any (none), a Sanctions exposure or PEP exposure indicator when the finding's text contains sanction or pep, and Critical aggregate network risk at a score of 85 or more. The drivers about relationship types describe the whole network, not the subject. The step is found where the engine's list holds a driver and not found where it is empty
