FND002 · Network Intelligence

Relationship Discovery

What connects these two entities, on what evidence, and how firmly?

The second half matters as much as the first. An edge asserted from a shared telephone number and an edge asserted from a filed directorship are both relationships, and an investigator must not weigh them alike.

FND002 Relationship Discovery is the foundation capability that derives typed, confidence-scored edges between resolved entities from six independent evidence sources, and reduces them to one non-duplicated set.

FND001 establishes who the nodes are. FND002 establishes what connects them. A typology such as PAT001 Shared Director is a question asked of this output — it does not discover the directorship, it interprets one FND002 has already found.

Risk indicators

Risk

  • Shared attribute edge read as evidence of control
  • Dense shared attribute cluster, the signature of a formation agent
  • Control edge sitting at exactly its default confidence
  • Ownership edge sitting at exactly its default confidence
  • Control asserted with no transactional edge between the parties
  • Transaction edge recorded from one side only
  • Edge whose only evidence source is an address match

Investigation actions

  1. Read the relationship category before the confidence score
  2. Treat Control, Ownership, Shared Attribute and Transactional as four different claims
  3. Count how many other entities share the value behind a shared attribute edge
  4. Treat an address shared by ninety entities as a service provider, not a network
  5. Check whether a control edge is supported by any transactional edge
  6. Treat a confidence sitting at exactly its default as absent rather than measured
  7. Read the evidence source recorded on each edge before relying on it

Detection logic

Six discovery passes run over the entity index, each emitting a typed edge:

Director pass emits DIRECTOR_OF, category Control, confidence default 0.95

Ownership pass emits BENEFICIAL_OWNER_OF, category Ownership, confidence default 0.93

Address pass emits SHARES_ADDRESS_WITH, category Shared Attribute, confidence fixed 0.90

Contact pass emits SHARES_CONTACT_WITH, category Shared Attribute, confidence fixed 0.88

Transaction pass emits TRANSACTS_WITH, category Transactional, confidence default 0.90

Trade pass emits TRADES_WITH, category Transactional, confidence default 0.92

The category is the load-bearing distinction, not the score. There are four of them and they answer different questions. Control asserts authority over an entity. Ownership asserts an economic stake, which is what FND003 walks into chains. Shared Attribute asserts only co-occurrence of a value — two companies at one serviced address share an address and may share nothing else. Transactional asserts a dealing. Reading a 0.90 address edge as comparable to a 0.93 ownership edge because the numbers are close is the misreading this list exists to prevent.

Two of the six relationship types are taken from the source record, with the value above as the fallback. An ownership record naming itself SHAREHOLDER_OF or ULTIMATE_OWNER_OF keeps that type, and only an unlabelled one becomes BENEFICIAL_OWNER_OF. A transaction record may likewise name its own type. The other four are fixed by the pass that emits them.

Confidence is carried from the source record for the four record-backed passes, and the defaults above apply only where the record supplies none. A score sitting at exactly its default therefore means the upstream source graded nothing — it is a fallback, not a measurement.

Shared attribute confidence is fixed outright and cannot be overridden, because the evidence is the match itself and admits no per-record grading. An address match is always 0.90 and a contact match always 0.88, never more and never less.

Edges are then deduplicated on the source entity, the target entity, the relationship type, the shared value, the transaction identifier and the trade identifier together. The last three belong in the key deliberately: two companies sharing two addresses are two pieces of evidence, not one duplicate, and collapsing them on entity pair and type alone would erase the second and understate the connection.
